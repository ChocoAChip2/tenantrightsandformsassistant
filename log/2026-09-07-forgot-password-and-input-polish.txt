Deployment Summary — Forgot/reset password, password visibility toggle, higher-contrast landing-page buttons
Date: 2026-09-07

Requirement (from conversation, not BRANCH-PLAN.md): three separate asks --
1. A forgot-password / reset-password feature -- there was previously no way
   to recover an account if a tenant forgot their password.
2. A show/hide toggle on password fields ("see password while typing"),
   using an eye emoji.
3. The buttons on the chat landing page (the greeting/suggestions screen
   shown right after logging in, before any conversation is open) were
   confirmed (via follow-up questions) to have low contrast -- they blended
   into the page and the hover state barely changed anything.

Changes shipped (branch fix/chat/forgot-password-and-input-polish, off main
after PRs #12-#17 merged):

1. Forgot/reset password:
   - supabase_service.py: new send_password_reset_email(email, redirect_to)
     wrapping auth.reset_password_email(). Supabase's underlying `recover`
     endpoint always returns success whether or not the email is
     registered (an intentional anti-enumeration design on Supabase's
     part), so this never tells the caller whether an account existed.
   - routes.py: two new routes.
     - GET/POST /forgot-password: collects an email, calls
       send_password_reset_email with redirect_to pointing at this app's
       own /reset-password route (url_for(..., _external=True)), and
       ALWAYS shows the same generic flash ("If an account exists for that
       email, we've sent a link to reset your password.") and redirects to
       /login -- regardless of whether the email exists or whether
       Supabase itself raised. This is deliberate: a different message or
       response code on failure vs. success would let the route be used to
       discover which emails are registered. Real failures are still
       logged server-side (logger.exception) for operators to see.
     - GET/POST /reset-password: sets the new password using access_token/
       refresh_token pulled from the POST body (see below for where those
       come from), reusing the same update_account(password=...) call
       settings.html's account form already uses -- there's no logged-in
       Flask session at this point (the visitor followed an emailed link,
       not a login), so these tokens are the only proof of identity.
       Missing tokens -> "invalid or expired" flash + redirect to
       /forgot-password. Mismatched or too-short password -> inline error,
       no Supabase call. A raised exception from update_account (e.g. an
       actually-expired recovery token) -> "Could not reset your password"
       flash + redirect to /forgot-password.
   - templates/forgot_password.html (new) and templates/reset_password.html
     (new): same card/token visual pattern as login.html/signup.html.
     reset_password.html is the one genuinely new piece of client logic:
     Supabase puts the recovery access_token/refresh_token in the URL
     *fragment* (#access_token=...&refresh_token=...&type=recovery), which
     browsers never send to a server, so a small inline script parses
     window.location.hash on load, copies the tokens into hidden form
     fields, then strips them from the visible URL via
     history.replaceState (they're sensitive and otherwise persist in
     browser history). If the tokens (or type=recovery) aren't present --
     an already-used link, a stale bookmark, someone landing on the page
     directly -- the form stays hidden and an "invalid or expired" notice
     shows instead, with a link back to /forgot-password.
   - templates/login.html: added a "Forgot password?" link under the
     password field.
   - IMPORTANT, needs a human with Supabase dashboard access: the
     /reset-password URL (e.g. https://<your-render-domain>/reset-password)
     must be added to this Supabase project's Auth -> URL Configuration ->
     Redirect URLs allowlist. Without that, Supabase will silently ignore
     the redirect_to option and send the recovery link to the project's
     default Site URL instead, and the flow above will never see the
     visitor. This can't be done from code -- it's a Supabase dashboard
     setting.

2. Password visibility toggle (all password fields, all 4 auth-adjacent
   pages -- login.html, signup.html, settings.html's two account fields,
   reset_password.html's two fields):
   - Each password <input> is now wrapped in a `.password-field` div with
     a `.password-toggle` button absolutely positioned inside it (input
     gets padding-right so the button doesn't overlap typed text).
   - Clicking the button flips the input's type between "password" and
     "text" and swaps the button's content between an eye emoji (showing,
     click to reveal) and a see-no-evil monkey emoji (currently revealed,
     click to hide) -- a common, immediately-recognizable pairing. aria-
     label/title update alongside the emoji for screen readers.
   - This is a small duplicated inline script per file (matching this
     codebase's existing pattern of duplicating shared CSS tokens and small
     scripts across the standalone-template files rather than a shared
     static asset) -- not a literal blinking animation, since an animated
     button felt at odds with the formal, civic-styled design direction
     from earlier in this project; happy to add a subtle pulse if that's
     actually wanted.

3. Chat landing-page button contrast (templates/chat.html):
   - .suggestion-chip (the "My landlord won't fix something" / "I got an
     eviction notice" / "Security deposit question" buttons on the
     greeting screen) previously used a near-invisible var(--border) as
     its only at-rest definition and just a subtle text-color shift on
     hover -- easy to miss entirely against the page background.
   - Now: added a small box-shadow at rest so the button reads as a
     raised, clickable surface even before interacting with it, bumped the
     label to font-weight 600, and hover/focus-visible now fills the
     background with var(--accent-tint) (the same "selected" treatment
     already used elsewhere on this page, e.g. the active conversation
     row) alongside the border/text color change -- a real, obvious state
     change instead of a faint one.

Verified locally:
- `python -m unittest discover -s tests` -- 81/81 pass (68 existing + 13
  new: 4 forgot-password route tests, 6 reset-password route tests, and 3
  SupabaseService unit tests for send_password_reset_email).
- HTML tag-balance check (html.parser) on every edited/new template --
  login.html, signup.html, settings.html, forgot_password.html,
  reset_password.html, chat.html -- no mismatches.
- `python -m py_compile` on every tracked .py file -- clean.

Deliberately not done:
- Did not add rate-limiting on /forgot-password itself (e.g. capping how
  often one email or IP can trigger a reset email) -- Supabase's own
  `recover` endpoint has its own rate limiting server-side, and adding a
  second layer felt like scope creep for this request. Worth revisiting if
  abuse becomes a real concern.
- Did not add a "resend link" affordance on reset_password.html's invalid-
  link state beyond the existing link back to /forgot-password.
- Did not add password-strength meters or additional password rules beyond
  the existing 6-character minimum -- kept consistent with what
  signup/settings already enforce rather than introducing a new standard
  only for this flow.
- Did not touch the "New password"/"Confirm new password" *validation*
  logic on settings.html or reset_password.html -- only added the
  visibility toggle to the existing fields.
- Did not add a literal blinking/pulsing animation on the password-toggle
  emoji -- see note above; can add if wanted.
